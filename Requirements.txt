fSONORA – iOS Music Player

Complete Project Requirements & Development Handover

Note: This document is a handover prompt for a new AI-assisted development conversation. It is written in Markdown-style formatting. Sections 18 and 19 record known architecture risks and additional requirements.

1. Project Overview

I want to build my own premium music player application for iPhone.

App Name: SONORA

Primary Objective:
Build a high-quality music player without advertisements, mandatory subscriptions or unnecessary restrictions.

I want to own and control my music library, store my music in cloud storage and play it on my iPhone without consuming too much device storage.

This is initially a personal-use application. I may consider publishing it on the Apple App Store in the future.

I have a Mac mini and an iPhone.

5. Cloud-First Music Management

This is one of the most important requirements.

I want cloud storage to act as my master music library.

The iPhone should primarily act as a playback device.

Expected behaviour:

* Music remains stored in cloud storage.
* Songs should stream when an internet connection is available.
* Songs should only be downloaded to iPhone when I explicitly request offline access.
* Downloaded songs should be available without internet.
* Deleting an offline download must NOT delete the original cloud file.
* Cloud originals should never be deleted automatically.
* Uploading a local file should preserve the original file.
* The application should clearly distinguish between cloud files and downloaded files.

Optional future feature:

A Smart Storage Manager that tracks local storage and helps remove old offline downloads while preserving cloud originals.

* ALAC
* MP3
* AAC

Requirements:

* Avoid unnecessary audio compression.

18. Architecture Risks

Resolve these before building the features they affect.

Risk 1: Cloud streaming vs. equalizer / audio effects
* AVPlayer can stream over HTTP but its audio cannot be routed through AVAudioEngine.
* Equalizer, Bass Boost, crossfade and ReplayGain need AVAudioEngine, which plays files or PCM buffers, not network streams.
* Options: (a) progressive download to a temporary cache file, then play it through AVAudioEngine; (b) a custom decode-and-buffer layer feeding AVAudioEngine; (c) use AVPlayer for streaming and apply effects only to downloaded/local tracks.
* Recommendation: design a single PlaybackEngine protocol so the engine can be swapped. Start with AVPlayer for local and streaming playback (Phase 1) and add the AVAudioEngine path in Phase 4. Document which features work on streamed tracks.

Risk 2: FLAC and other non-native formats
* AVFoundation reads local FLAC through AVAudioFile on recent iOS, but HTTP streaming of FLAC is unreliable.
* Options: a decoder library (libFLAC, SFBAudioEngine), or progressive download of FLAC before playback.
* Verify on the target iOS version with real FLAC files before committing.

Risk 3: Gapless playback and crossfade
* Both are easiest on the AVAudioEngine path (scheduling buffers back to back). AVPlayer gapless behaviour is limited.
* Treat them as Phase 4 features tied to the engine decision in Risk 1.

Risk 4: MEGA
* No official streaming-friendly iOS API; files are end-to-end encrypted, so plain HTTP range requests do not work.
* Keep it optional and last. Do not let it shape the cloud abstraction.

Risk 5: Cloud abstraction
* Define a CloudProvider protocol (auth, list, search, stream URL or byte-range read, download, upload, quota) so each provider is a plug-in.
* Token refresh and expiry handling live in one place.

Risk 6: Database choice
* SwiftData needs iOS 17+. If the target iPhone is older, use SQLite (GRDB). Decide in Phase 1.

Risk 7: CarPlay
* Requires an Apple-approved entitlement and a paid developer account. Keep playback and library logic independent of the UI so a CarPlay scene can reuse it.

Risk 8: Copyright and platform terms
* Metadata search must not become an unlicensed download path. See Section 9.

19. Additional Requirements

* Network resilience: buffering indicators, automatic retry with backoff, graceful behaviour when a stream drops mid-track, and fallback to the offline copy when one exists.
* Local/cloud duplicates: when the same song exists locally and in the cloud, treat it as one library item, prefer the offline copy for playback, and show both states.
* Large libraries: the library must stay responsive with thousands of songs; use paging for cloud folder listings and lazy artwork loading.
* Cloud indexing: index cloud metadata without downloading whole files (read tags via range requests where possible, cache results locally).
* Accessibility: VoiceOver labels, Dynamic Type and sufficient contrast in the dark theme.
* Testing: unit tests for the library, queue and cloud provider layers; manual test checklists for background playback, lock screen, interruptions (calls, Siri), route changes (Bluetooth, headphones) and offline mode; test on a real iPhone.
